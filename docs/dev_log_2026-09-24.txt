======================================================================
1. THE SYSTEM IN ONE PICTURE
======================================================================

A student types a question. The system turns it into a search, gets results from UB's
OneSearch, picks the best 1-3, and writes a short answer with real links and shelf locations.

   user question + role
          |
          v
   [PLAN]     LLM turns the sentence into keywords + filters
          |     "find me peer reviewed journals on mental health"
          |      -> keywords "mental health", type "journals", peer-reviewed yes
          v
   [SEARCH]   Layer 1 searches OneSearch (retries once without filters if nothing found)
          |
          v
   [RAG]      placeholder for now (returns nothing)
          |
          v
   [COMPOSE]  LLM picks the best 1-3 results and says why
          |     code then fetches their links / call numbers and writes the final answer
          v
   answer text

Layer 1 = the "onesearch/" folder (talks to UB's website). Layer 2 = the "agent/" folder
(the LLM part that decides what to search and what to show).


======================================================================
2. WHAT EACH CODE MODULE DOES
======================================================================

--- Layer 1: onesearch/  (talks to UB OneSearch; knows nothing about LLMs) ---

onesearch/session.py
   Opens a hidden browser (Playwright) once, so UB's site gives us session cookies.
   The cookies are reused for 15 minutes so we do not open a browser for every search.

onesearch/client.py
   The main door to OneSearch.
   - search(query, resource_type, peer_reviewed): returns up to 10 results.
     The two filters (books/articles/journals/dissertations/videos, and peer-reviewed)
     are sent to UB as "facets".
   - fetch_detail(ids): ONE batched call that gets the "view online" link for the chosen
     items; physical items (call number, library, availability) are remembered from search.
   - search_with_fallback(): search with a time limit; if too slow, returns a direct
     OneSearch link instead of hanging.
   - fallback_link() / record_link(): build OneSearch web page links.

onesearch/parser.py
   Reads UB's raw JSON and pulls out title, author, date, type, subject, description,
   call number, library, availability, and online link.

onesearch/models.py
   Simple data containers: SearchCandidate, ResourceDetail, SearchResult.

onesearch/cache.py
   Remembers search results for a few minutes so repeated searches do not hit UB again.

onesearch/verify_live.py
   Manual script (not a test). Runs real searches against UB and prints every result with
   its details. Saved output: docs/verify_live_output.txt

--- Layer 2: agent/  (the LLM part) ---

agent/models.py
   Data shapes: QueryPlan (keywords + filters), Selection (which results to show),
   AgentState (what is passed between steps), ROLES (undergraduate/graduate/faculty).

agent/llm.py
   Builds the chat model. Choose with settings: LLM_PROVIDER = openai, anthropic or local.
   "local" uses Ollama, or any OpenAI-style local server through LLM_BASE_URL.
   Gives a clear error if a key or package is missing.

agent/planner.py
   LLM call 1. Turns the user's sentence into keywords + filters.
   If the model fails or gives junk, it falls back to searching the raw sentence.

agent/onesearch_tool.py
   The bridge between Layer 2 and Layer 1. Runs the search. If a filtered search finds
   nothing, it searches ONE more time without filters and adds a note saying so.
   If UB is down or slow, it returns a direct OneSearch link instead of crashing.

agent/compose.py
   LLM call 2 + final answer. The LLM only picks IDs and gives a one-line reason.
   Code then checks the IDs are real (max 3), fetches the details, and writes the answer.
   Links and shelf locations always come from real data, never from the LLM.

agent/graph.py
   Connects plan -> search -> rag -> compose (LangGraph). Records how long each step took.
   If the planner asks a clarifying question, the turn stops there.

agent/cli.py
   The chat program you run: python -m agent.cli
   Asks for your role, then chats. /role changes role, /quit exits, --debug shows the plan
   and timings. Options: --provider and --model.

agent/live_check.py
   Manual script (not a test). Runs two real questions through the whole system with a
   real model. Saved output: docs/layer2_live_check_output.txt

--- Tests and helpers ---

tests/fakes.py            A fake LLM so tests run with no internet and no API key.
tests/test_*.py           84 tests in total, all offline.
pytest.ini                Lets you just type "pytest".
requirements-optional.txt Extra packages only needed for anthropic / local providers.

5. ISSUES THAT NEED A LOOK (please review these)
======================================================================

MOST IMPORTANT

  1. SPEED WITH THE LOCAL MODEL. A full answer took 58.8 s and 38.7 s. The target is 3-6 s.
     The compose step alone took about 30 s (the first plan call took 23 s, which includes
     loading the model). Search is fine (2-5 s). Likely cause: the compose prompt sends 10
     results with long descriptions to a 14B model. Ideas to try: send only the top 5
     results, shorten descriptions, use a smaller model for planning, or use a hosted model
     (OpenAI / Anthropic) for compose. DECISION NEEDED from you.

  2. OPENAI AND ANTHROPIC ARE NOT TESTED LIVE. Only the local Ollama model was run for real.
     The OpenAI and Anthropic paths are only covered by tests with fake models. Need one live
     run each once you have keys.

  3. ANSWER QUALITY WITH A REAL MODEL IS ONLY SPOT-CHECKED. We ran 2 questions. There is no
     evaluation set yet (RAGAS is planned for a later slice). Follow-up questions ("what
     about books?") that rely on conversation history have NOT been tried live.

  4. FOLLOW-UP HISTORY SENDS WHOLE ANSWERS. The chat program stores each full answer text in
     the history and passes the last 3 into the planner prompt. Answers are long, so this
     makes the planner prompt big and slow. Better: store only the previous keywords/filters.

THINGS THAT WORK BUT ARE ROUGH

  5. SOME RESULTS HAVE NO LINK OR LOCATION. Records from the e-book catalog (record IDs
     starting "cdi_", for example "Baseball in Buffalo") get nothing from /edelivery. The
     answer shows only the OneSearch record page link. Not wrong, but not ideal.

  6. "MORE RESULTS" LINK DROPS THE FILTERS. The fallback link only carries the keywords, so
     it opens an unfiltered search. We did not find UB's web-page filter parameter yet.

  7. JOURNAL "AUTHOR" IS THE PUBLISHER/ISSUING BODY. Journals show text like
     "International Center of Mental Health Policy and Economics, issuing body". Cosmetic.

  8. SOME ONLINE LINKS NEED A UB LOGIN. Some links redirect to gate.lib.buffalo.edu/login.
     The answer includes a general note about this, but it does not say which links.

  9. NO "COPIES AVAILABLE" NUMBER. UB does not send one. We only show
     available / currently unavailable / check holdings.

 10. "PEER REVIEWED JOURNALS" IS AMBIGUOUS. It can mean journal titles, or articles from
     peer-reviewed journals. The planner prompt allows asking a clarifying question, but we
     have not seen how the local model handles this case.

 11. REFINE-ONCE ONLY DROPS FILTERS. If a search with no filters finds nothing, we do not
     rewrite the keywords (that would need another LLM call). The user just gets the
     "no results" message with a direct link.

RISKS TO KEEP IN MIND

 12. UB'S ENDPOINT IS UNOFFICIAL. We use the same internal calls the website uses. It can
     change without notice (it already changed once: the "network idle" behaviour). The
     official Ex Libris guest API is the documented fallback. UB Libraries has raised a
     security concern before, so keep the request volume low and the User-Agent honest.

 13. COLD START IS SLOWER THAN THE TARGET. Session start took 4.7-5.4 s (target was 2-4 s).
     It happens about once every 15 minutes.

 14. MEMORY GROWS SLOWLY. The client remembers every result it has seen (for physical
     locations) and never forgets. Fine for a demo, should be capped for a long-running app.
     After a timeout the slow search keeps running in the background until it finishes.

 15. PACKAGES ARE NOT PINNED. requirements.txt lists package names without versions. Today's
     working versions: langgraph 1.2.12, langchain-core 1.6.5, langchain-openai 1.6.6,
     langchain-ollama 1.1.0, pydantic 2.13.5. Consider pinning.

HOUSEKEEPING
